ANDROID CALL RESERVATION HELPER - STANDALONE APP OUTLINE

Repository name suggestion:
android-call-reservation-helper

Purpose:
A standalone Android app for restaurant staff who take reservation calls. The app detects incoming phone calls, ignores whitelisted numbers, shows a floating reservation form during eligible calls, keeps the form open after the call ends, and creates a Google Calendar event after the user submits the reservation.

Core user flow:
1. User opens the app.
2. User grants required permissions.
3. User configures whitelisted numbers that should not trigger the reservation popup.
4. User selects the target Google Calendar.
5. An incoming phone call arrives.
6. App checks the caller number.
7. If the caller is whitelisted, no popup appears.
8. If the caller is not whitelisted, a floating reservation form appears over the call screen.
9. User fills in reservation details during the call or after the call ends.
10. User submits the form.
11. App creates a Google Calendar event.
12. App saves the reservation submission to local history.
13. User can open the app later to review past calendar updates.

Main features:

1. Setup screen
- Shows permission status.
- Requests phone state permission.
- Requests contacts/call log permission if caller number matching is needed.
- Requests calendar read/write permission.
- Requests overlay permission for floating popup windows.
- Shows battery optimization warning and asks user to disable battery restrictions for reliability.

2. Dashboard screen
- Shows whether the app is active.
- Shows current selected calendar.
- Shows number of whitelisted numbers.
- Shows recent reservation submissions.
- Provides quick buttons:
  - Test popup
  - Manage whitelist
  - View history
  - Calendar settings
  - App permissions

3. Whitelist screen
Purpose:
Numbers in the whitelist should not trigger the reservation popup.

Features:
- Add number manually.
- Add number from contacts.
- Edit existing whitelisted number.
- Delete whitelisted number.
- Optional label for each number.
- Normalize phone numbers before comparison.

Example whitelist record:
- name: Owner
- phone: +14165551234
- note: Do not show reservation popup for this caller.

Recommended matching behavior:
- Store phone numbers in normalized E.164 format when possible.
- Also support loose matching by final 10 digits as fallback.
- If incoming number is hidden/private/unknown, treat it as non-whitelisted unless the user disables unknown-number popups.

4. Call detection
Purpose:
Detect incoming calls and decide whether to show the reservation overlay.

Expected behavior:
- Listen for ringing/offhook phone states.
- Capture incoming caller number when Android provides it.
- Check number against whitelist.
- If caller is not whitelisted, start overlay service.
- Do not auto-close overlay when the call ends.

Important Android limitation:
Caller number access may be restricted on some Android versions/devices. The app should still show the popup and let the user manually enter the phone number if the caller number is unavailable.

5. Floating reservation popup
Purpose:
Allow the user to fill in reservation information while on the call.

Behavior:
- Appears above the phone call screen.
- Stays open after the call ends.
- Can be moved or minimized if possible.
- Does not block the user from using the phone call controls.
- Contains required reservation fields.
- Submits to Google Calendar.

Fields:
- Customer name
- Phone number
- Reservation date
- Reservation time
- Party size
- Duration
- Notes

Required fields:
- Customer name
- Date
- Time

Optional fields:
- Phone number
- Party size
- Duration
- Notes

Recommended default duration:
240 minutes

Popup buttons:
- Create calendar event
- Save draft
- Minimize
- Close

Validation:
- Name cannot be empty.
- Date must be valid.
- Time must be valid.
- If party size is entered, it must be a positive number.
- If validation fails, show a clear error message and keep the form open.

6. Calendar integration
Purpose:
Create a Google Calendar event from the completed reservation form.

Event title format:
Reservation - {Customer Name}
Reservation - {Customer Name} - {Party Size} people, when party size is entered

Example:
Reservation - Alex - 4 people

Event description format:
Customer: Alex
Phone: 416-555-1234
Party size: 4
Notes: Birthday dinner

Event time:
- Start time: selected date and time.
- End time: start time + selected/default duration.

Calendar selection:
- User chooses the target calendar during setup.
- If no calendar is selected, use the primary writable calendar.
- If direct calendar insert fails, fallback to opening Google Calendar with a prefilled event.

7. Reservation history screen
Purpose:
Show past submissions and calendar updates.

History item fields:
- Customer name
- Phone number
- Date and time
- Party size
- Calendar event ID if available
- Creation timestamp
- Status: created, draft, failed, deleted, opened in calendar
- Error message if creation failed

Features:
- View reservation details.
- Reopen reservation.
- Retry failed calendar insert.
- Open event in Google Calendar if event ID/deep link is available.
- Delete local history record.
- Search by customer name or phone number.
- Filter by date.

8. Draft reservations
Purpose:
Let the user save incomplete reservations without creating calendar events.

Behavior:
- User can tap Save Draft from the popup.
- Draft appears in the app history.
- User can complete and submit the draft later.

9. Settings screen
Settings:
- Enable/disable call popup.
- Popup behavior for unknown/private numbers.
- Default reservation duration.
- Default calendar.
- Whitelist mode.
- Auto-fill caller number when available.
- Keep popup open after call ends.
- Show popup on incoming calls only, outgoing calls only, or both.
- Enable test mode.

Whitelist mode options:
- Ignore whitelisted numbers: popup appears for everyone except listed numbers.
- Only allow listed numbers: popup appears only for listed numbers.

Recommended default:
Ignore whitelisted numbers.

10. Permissions required
Runtime permissions:
- READ_PHONE_STATE: detect phone call state.
- READ_CALL_LOG: may be needed to access incoming number on some devices.
- READ_CONTACTS: optional, for selecting whitelist contacts.
- READ_CALENDAR: list available calendars.
- WRITE_CALENDAR: create calendar events.
- SYSTEM_ALERT_WINDOW: show popup over phone call screen.

Other requirements:
- Battery unrestricted mode recommended.
- Foreground service recommended for reliability.

14. Calendar event creation strategy
Primary strategy:
Use Android Calendar Provider to directly insert the event.

Fallback strategy:
Use Intent.ACTION_INSERT with CalendarContract.Events.CONTENT_URI to open Google Calendar prefilled.

Reason for fallback:
Some devices/calendars may reject direct inserts or lack a writable calendar.

15. Reliability considerations
- Use a foreground service when showing the overlay.
- Do not destroy the popup when the call ends.
- Save form state locally while the popup is open.
- Restore unsaved form if the overlay is killed.
- Let the user manually open a test popup from the dashboard.
- Handle private/unknown numbers gracefully.
- Make phone number field editable.
- Keep all date/time input strict in the first version.

18. Minimum viable version
The first usable version only needs:
- Permission screen.
- Test popup.
- Incoming call detection.
- Whitelist ignore list.
- Floating form.
- Calendar insert.
- Basic history.

Do not include AI, transcription, or call recording in the first version.

19. Main risks
- Caller number may not be available on all Android builds.
- Overlay permission must be granted manually.
- Background restrictions may prevent reliable popup behavior without foreground service.
- Some calendars may not allow direct inserts.
- Different phone manufacturers may behave differently during call UI overlays.

20. Recommended final behavior
When a non-whitelisted call arrives, the app should show a compact overlay immediately. The user can fill in the reservation during the call, ignore it, minimize it, or finish it after the call. Submitting creates a calendar event and stores a local history record. The app should remain useful even if caller number autofill fails.
